# JobFit

JobFit 是一个面向学生与初入职场求职者的 AI 简历定制 Web 应用。它帮助用户理解岗位要求，并基于用户**已经提供且可追溯的真实经历**，生成更匹配目标岗位的简历；它不是代写虚假经历的工具。

> 当前阶段：已接入真实岗位 JD 分析；本文同时保留后续产品与技术规划。

## 当前实现

仓库目前包含一个可以本地运行的 Next.js Web 应用骨架：

- 简洁、响应式的 JobFit 首页，介绍产品价值、五步流程和真实性原则；
- `/analyze` 岗位分析页，支持粘贴 JD 或填入示例 JD；
- 点击“分析岗位”后通过服务端 Route Handler 调用 OpenAI，展示核心能力、关键词、岗位职责和加分项；
- 当前不会上传文件、连接数据库、实现登录或生成 PDF。

### 本地启动

环境要求：Node.js 20.9 或更高版本，推荐使用当前 LTS 版本。

```bash
npm install
cp .env.example .env.local
npm run dev
```

在 `.env.local` 中填写你自己的 `OPENAI_API_KEY`。密钥只由服务端读取，不要使用
`NEXT_PUBLIC_` 前缀，也不要提交 `.env.local`。可选的 `OPENAI_MODEL` 用于覆盖默认模型。

打开 [http://localhost:3000](http://localhost:3000)，或访问 [http://localhost:3000/analyze](http://localhost:3000/analyze) 直接体验岗位分析。

### 可用命令

```bash
npm run dev        # 启动本地开发服务器
npm run lint       # 运行 ESLint
npm run typecheck  # 运行 TypeScript 类型检查
npm run build      # 创建生产构建
npm start          # 启动已构建的生产服务
```

本阶段刻意不包含登录、数据库、支付、文件解析、OCR 和真实 AI 集成。`.env*`、本地上传目录和常见私人简历文件名均已加入 `.gitignore`；请勿将真实简历或 API Key 提交到仓库。

## 1. 产品目标与原则

### 核心问题

学生通常拥有课程项目、社团、实习、竞赛等分散经历，却难以：

1. 从冗长 JD 中识别真正重要的能力、关键词与职责；
2. 判断自己的哪些经历与岗位最相关；
3. 用招聘方熟悉的语言重写简历，同时避免夸大或虚构；
4. 针对多个岗位高效地产出不同版本，并清楚知道改了什么。

### 产品原则

- **真实性优先**：所有生成内容必须能回溯到用户输入的事实证据。
- **用户掌控**：AI 只给建议和草稿，用户确认后才能进入最终简历。
- **可解释**：展示 JD 要求、匹配依据、未满足项和每项改写的来源。
- **最小化收集**：简历属于高敏感个人数据，只保存完成任务所必需的信息。
- **不承诺结果**：匹配分用于解释内容相关度，不等同于 ATS 分数或录用概率。

## 2. 核心用户流程

1. **创建一次求职任务**
   - 用户粘贴 JD，或上传 JD 的图片/PDF。
   - 系统完成文本提取；用户先预览和纠正识别结果。
2. **理解目标岗位**
   - AI 将 JD 解析为岗位信息、核心职责、硬技能、软技能、关键词和资格条件。
   - 系统区分“必需 / 加分 / 不明确”，并保留对应的 JD 原文证据。
   - 用户可以修改或确认分析结果，避免错误解析影响后续生成。
3. **建立候选人事实库**
   - 用户上传 PDF/DOCX 简历，或在表单中补充教育、实习、项目、社团、技能等经历。
   - 系统结构化提取事实，并提示用户确认；不确定或缺失信息保持为空，不能自动补齐。
4. **匹配经历与岗位**
   - 系统把 JD 要求与事实库中的经历/要点进行相关性匹配。
   - 用户看到“匹配项、依据、证据来源、缺口”，并可选择要纳入目标简历的内容。
5. **生成定制简历草稿**
   - AI 只能使用已确认事实，优化排序、措辞和关键词表达。
   - 每条生成要点携带事实引用；没有证据的内容不得出现在草稿中。
6. **审阅与导出**
   - 用户逐条接受、修改或拒绝建议，查看原文与改写差异及来源。
   - 用户完成真实性确认后，导出为 PDF；原始事实库保持不变，定制版本单独保存。

### 关键异常流程

- 文件无法解析、含扫描页或 OCR 置信度低：标记具体页/段，要求用户校正或改用粘贴文本。
- JD 信息不足：允许继续，但明确显示“不明确”，不推断公司、薪资或隐藏要求。
- 用户经历无法覆盖某项要求：显示为能力缺口，建议用户补充真实证据或从简历中略去，绝不生成补位经历。
- AI 输出引用了不存在的事实：自动校验失败并丢弃该条输出，不能展示为可用草稿。

## 3. MVP 范围

### 第一版必须做（可真正跑通的闭环）

| 模块 | MVP 能力 | 验收标准 |
| --- | --- | --- |
| 账户与隐私 | 邮箱登录；用户数据隔离；删除求职任务与原文件 | 未登录不可访问；用户只能访问自己的数据；删除后任务不可恢复 |
| JD 输入 | 粘贴文本；上传单个 PDF/PNG/JPEG；文本预览与人工修正 | 能形成一份用户确认的标准化 JD 文本 |
| JD 分析 | 提取职责、技能、关键词、资格条件，并标注优先级与原文依据 | 每项分析都有 JD 片段引用；用户可编辑确认 |
| 简历输入 | 上传单个 PDF/DOCX；结构化预览；表单补充/修正经历 | 每条事实有稳定 ID、来源和确认状态 |
| 事实匹配 | 将 JD 要求匹配到经历要点，展示依据和未覆盖项 | 用户能选择用于生成的真实经历；不把语义相似当作事实证明 |
| 定制生成 | 生成摘要（仅证据充分时）、经历要点和技能排序建议 | 每条生成文本都有事实引用，事实校验通过后才能展示 |
| 审阅 | 原文/建议对照；接受、编辑、拒绝；真实性确认 | AI 不能静默覆盖原始简历；用户可以完成最终确认 |
| 导出 | 提供一种固定单栏模板并导出 PDF | 导出内容与审阅后的版本一致，文本可选择/复制 |
| 基础运维 | 文件类型/大小限制、错误提示、结构化日志、AI 调用追踪 | 失败可定位到处理阶段；日志不记录完整简历正文 |

MVP 不追求“自动完成一切”，而是验证一条可信闭环：**输入 JD → 确认要求 → 输入并确认事实 → 匹配 → 有证据的改写 → 人工审阅 → PDF 导出**。

## 4. 推荐技术栈

初期采用**单体优先、边界清晰**的方案，降低部署和调试成本；只有文件处理等耗时任务通过后台 Worker 解耦。

| 层 | 选择 | 理由 |
| --- | --- | --- |
| Web | Next.js + TypeScript + React | 页面、服务端接口和类型可在一个仓库中维护，适合快速验证完整流程 |
| UI | Tailwind CSS + 可访问的无样式组件库 | 快速构建一致界面，同时保留设计控制权；组件需满足键盘操作与语义化要求 |
| 表单/校验 | React Hook Form + Zod | 同一份 Schema 可用于表单和服务端边界校验，减少结构化 AI 输出带来的类型风险 |
| 数据库 | PostgreSQL + Prisma | 关系模型适合用户、任务、版本、事实引用等强关联数据；JSON 字段可承载迭代中的 AI 结构 |
| 认证 | Auth.js（或托管认证服务） | MVP 支持邮箱登录与会话即可；封装在适配层内，避免业务代码绑定供应商 |
| 文件存储 | S3 兼容对象存储 | 原文件不进入数据库；支持私有对象、短期签名 URL、生命周期与删除策略 |
| 后台任务 | Redis + BullMQ Worker | OCR、解析和生成可能超出请求时限；提供重试、超时与任务状态。流量很小时可先用数据库任务表实现 |
| 文档处理 | `pdf-parse`/PDF.js、Mammoth；OCR 使用托管文档识别服务 | 原生文本优先，OCR 只处理无文本层页面；DOCX 提取以语义内容为主而非复刻样式 |
| AI | 支持结构化输出的 LLM，经自有 Provider 接口调用 | 业务依赖内部 Schema 而非特定厂商；便于替换模型、控制超时、重试和审计 |
| 导出 | HTML/CSS 打印模板 + Playwright/Chromium | 单一模板可稳定复现，PDF 保留文本层，且便于端到端视觉检查 |
| 测试 | Vitest + Testing Library + Playwright | 覆盖纯函数/Schema、关键交互和完整主流程 |
| 部署/观测 | Web 与 Worker 分开部署；Sentry + 结构化日志 | 故障可按 `request_id`、`job_id`、`ai_run_id` 追踪，同时对个人信息脱敏 |

不在 MVP 引入微服务、Kubernetes 或向量数据库。候选人早期数据量小，PostgreSQL 全文检索与应用层语义匹配足够；确有规模和召回率证据后再引入 embedding/向量索引。

## 5. 整体架构

```text
Browser
  │ HTTPS
  ▼
Next.js Web（页面、BFF/API、鉴权、输入校验）
  ├── PostgreSQL（业务数据、状态、版本、审计元数据）
  ├── Private Object Storage（原始文件、短期产物）
  └── Job Queue ──► Worker
                    ├── PDF/DOCX 文本提取
                    ├── OCR / 文档识别
                    ├── AI Gateway ──► LLM Provider
                    ├── 事实与引用校验
                    └── PDF 渲染
```

### 模块边界

- **Web/BFF**：认证授权、上传签名、任务状态、用户编辑和响应 DTO；所有对象查询都带 `user_id`。
- **Document Ingestion**：文件安全检查、文本提取、页码/段落定位、OCR 和规范化；不负责生成内容。
- **JD Analyzer**：只从确认后的 JD 文本生成结构化要求，并记录原文引用。
- **Candidate Fact Store**：保存原始资料提取结果与用户确认事实；它是生成内容的唯一事实来源。
- **Matcher**：给要求与事实建立相关性边，不改变任何事实。
- **AI Gateway**：统一模型请求、Schema 校验、超时、有限重试、提示词版本、成本与调用元数据。
- **Resume Composer**：按用户选择组织内容，执行引用与事实约束，产出不可变版本。
- **Exporter**：只读取已确认版本并渲染，不再次调用 AI。

### 状态机与可靠性

求职任务使用显式状态，避免客户端猜测后台进度：

```text
draft → ingesting_jd → jd_review → ingesting_resume → facts_review
      → matching → match_review → generating → resume_review → ready
                               ↘ failed（可从失败步骤重试）
```

后台任务必须具备幂等键、超时和有限次数重试。同一个输入版本重复执行不应创建重复事实；用户编辑后创建新版本，不覆盖已经确认/导出的版本。

## 7. 核心数据结构

下列是概念模型，不是最终数据库迁移。所有主键推荐使用 UUID；时间字段包括 `created_at`、`updated_at`，重要内容记录 `version`。

```ts
type SourceRef = {
  documentId: string;
  page?: number;          // PDF/图片定位
  section?: string;       // DOCX/表单定位
  startOffset?: number;
  endOffset?: number;
  quote: string;          // 短证据片段，必须能在规范化源文本中找到
};

type JobRequirement = {
  id: string;
  category: "responsibility" | "hard_skill" | "soft_skill" | "qualification" | "keyword";
  text: string;
  priority: "required" | "preferred" | "unclear";
  sourceRefs: SourceRef[];
  confirmedByUser: boolean;
};

type CandidateFact = {
  id: string;
  experienceId: string;
  kind: "role" | "action" | "skill" | "tool" | "outcome" | "metric" | "date" | "education";
  value: string;
  sourceRefs: SourceRef[];
  confirmation: "pending" | "confirmed" | "rejected";
};

type Match = {
  requirementId: string;
  factIds: string[];
  relevance: "high" | "medium" | "low";
  rationale: string;      // 解释相关性，不构成新事实
};

type GeneratedBullet = {
  id: string;
  text: string;
  factIds: string[];      // 必填；引用的事实必须为 confirmed
  requirementIds: string[];
  validation: "pending" | "passed" | "failed";
  userDecision: "pending" | "accepted" | "edited" | "rejected";
};
```

### 主要实体关系

- `User` 1—N `JobTarget`：一个用户可创建多个目标岗位任务。
- `JobTarget` 1—N `Document` / `JobRequirement` / `Match` / `ResumeVersion`。
- `User` 1—N `Experience`；`Experience` 1—N `CandidateFact`，事实可被多个岗位复用。
- `Document` 1—N `DocumentChunk`，保留页码、段落和字符范围用于引用。
- `AIRun` 记录步骤、模型、提示词版本、输入/输出 Schema 版本、状态、耗时和 token 用量；默认不把完整敏感正文写入日志。
- `ResumeVersion` 是快照，包含布局数据和 `GeneratedBullet`；已导出版本不被后续编辑覆盖。

原文件与解析文本分离存储。数据库只保存私有对象键，不保存公开 URL；下载使用短期签名 URL。设置明确的数据保留和级联删除策略。

## 8. 文件处理策略

### 通用上传安全

1. 浏览器只做体验性检查；服务端重新校验扩展名、MIME、文件签名、页数与大小。
2. 使用随机对象键和私有存储，禁止执行文件内容；可接入恶意文件扫描。
3. 文档处理在隔离 Worker 中运行，设置 CPU、内存和超时限制，防范解析器漏洞与压缩炸弹。
4. 对文本做 Unicode 规范化、去除重复页眉页脚，但保存原始文本及页/段映射。
5. 解析结果必须经用户预览确认，之后才可进入 AI 流程。

### 岗位 JD 图片（PNG/JPEG）

- 自动纠正旋转、缩放过大的图片，必要时进行对比度和去噪预处理。
- OCR 返回文本块、位置和置信度；按视觉布局恢复阅读顺序。
- 低置信度文字醒目标注，让用户对照原图修正；不要把猜测结果直接交给 AI。
- MVP 支持单张或受限数量图片，超限时提示合并为 PDF 或粘贴文本。

### 岗位 JD PDF

- 先检测每页是否有可用文本层，并直接抽取文字和页码映射。
- 仅对无文本层或文本质量异常的页面进行栅格化 OCR，避免不必要的成本与误差。
- 处理双栏布局、分页断句和重复页眉页脚；最终展示规范化全文供用户校正。
- PDF 内链接或脚本一律不执行；加密或损坏文件给出明确的替代输入方式。

### 简历 PDF

- 与 JD PDF 使用同样的“文本层优先、逐页 OCR 兜底”策略。
- 额外识别标题、教育、经历、项目、技能等区域，但保留阅读顺序与页码证据。
- 多栏、图标式技能和复杂表格可能丢失语义，应显示解析预览并鼓励用户补录。
- 不以视觉位置自行推断雇佣关系或日期；跨段关联不确定时标记待确认。

### 简历 DOCX

- 在隔离环境解析 OOXML，拒绝宏相关格式；忽略外部资源和远程链接。
- 提取段落、标题、列表、表格和超链接文字，建立到 OOXML 段落的来源引用。
- 批注、修订和隐藏文本默认不作为候选事实，并提示用户文档中存在这些内容。
- MVP 不承诺复刻用户原有排版；只提取语义内容，最终使用 JobFit 固定模板导出。

任何格式都不能仅凭文件解析结果进入生成：**解析文本 → 结构化候选事实 → 用户确认**是必经步骤。

## 9. AI 工作流

AI 每一步只完成一个受限任务，并通过严格 JSON Schema 交换数据：

1. **JD 结构化**
   - 输入：用户确认的 JD 文本与带定位的片段。
   - 输出：`JobRequirement[]`；每项必须引用输入片段，不得补充行业常识为岗位要求。
2. **简历事实抽取**
   - 输入：简历文本块。
   - 输出：经历候选项和原子 `CandidateFact[]`；不确定信息为空并标记待确认。
   - 用户确认后才写入可用于生成的事实集合。
3. **要求—事实匹配**
   - 输入：已确认要求和事实（使用不可混淆的 ID）。
   - 输出：`Match[]` 和未覆盖要求；理由只能解释已有内容。
4. **受约束改写**
   - 输入：用户选中的 confirmed facts、目标要求、写作规则和长度限制。
   - 输出：`GeneratedBullet[]`；每条必须列出使用的 `factIds`。
5. **确定性验证 + AI 复核**
   - 程序先验证 ID 存在、状态为 confirmed、日期/数字/专有名词是否有精确事实支持。
   - 再用独立的“事实审校”步骤逐项判断是否蕴含无证据主张；失败条目丢弃或退回重写。
6. **人工确认与版本化**
   - 界面显示生成句、引用事实和来源片段。用户编辑新增事实性内容时，也需要绑定已有事实或明确补充并确认新事实。
   - 保存最终快照和决策，不覆盖原始事实。

每个阶段都保存输入数据版本、Schema 版本与提示词版本，使问题可复现；缓存键必须包含这些版本。模型返回的 JSON 即使语法有效，也必须经过业务校验才能持久化。

## 10. 防止 AI 编造的约束设计

单靠提示词无法保证真实性，需要“数据、提示、校验、交互、审计”五层防线。

### 1）事实白名单

- 只有用户明确确认的 `CandidateFact` 能进入生成上下文。
- 将复合描述拆成角色、动作、工具、结果、数字、日期等原子事实，避免模型自由补全关系。
- 数字、百分比、规模、排名、时间、技能熟练度、公司/项目名称都按高风险事实处理。
- 用户没有提供量化结果时，可以优化动作和影响的表达，但不能生成任何数字，也不能把“参与”升级为“主导”。

### 2）最小上下文与结构化输出

- 生成模型只看到选中的事实和 JD 要求，不接触未确认的抽取结果。
- 系统提示明确禁止新增项目、雇主、职位、技能、工具、证书、日期、指标、职责范围和因果关系。
- 输出必须符合 JSON Schema；每条建议必须附 `factIds`，无引用即为无效。
- 明确允许模型回答“证据不足，无法生成”，不强迫凑满条目。

### 3）确定性守卫

- 拒绝未知、已拒绝或属于其他用户的事实 ID。
- 对生成文本中的数字、日期、货币、百分比和专有名词做抽取，与所引事实逐项比对；新增项直接失败。
- 检查技能词只能来自已确认技能事实，或作为 JD 词汇用于描述已有且等价的事实；等价关系不明确时必须人工确认。
- 限制模型只能改写文本，排序与选取由程序和用户控制；验证失败不能通过重试悄悄放宽规则。

### 4）语义审校与用户界面

- 独立审校器只做 entailment 判断：每个主张是否被引用事实完整支持，而不是评价文采。
- 高风险动词（如“领导”“设计”“独立负责”“提升”）若源事实只有“参与/协助”，判为越权改写。
- UI 在每条建议旁展示证据；把无覆盖要求显示为缺口，而不是生成“合理猜测”。
- 用户自由编辑后的文本重新运行同样检查；新增事实先进入事实库确认流程。

### 5）审计与评测

- 保存生成版本、引用关系、验证结果和用户决策，便于复现，不在普通日志中记录完整个人资料。
- 建立红队测试集：无指标经历、相似但不同技能、时间冲突、提示注入式 JD、跨经历错误拼接等。
- 核心质量指标包括：无证据主张率（目标为 0）、引用完整率、抽取修正率、用户拒绝率，而非只看生成接受率。
- JD 和简历内容均视为**不可信数据**；其中类似“忽略规则”的文本不能成为模型指令。

示例：事实为“协助 3 人小组整理 200 份问卷”，允许改写为“协助 3 人团队整理 200 份问卷”；不允许改为“领导团队完成用户研究，使效率提升 30%”，因为领导关系、研究结论和提升比例都无证据。

## 11. 隐私、安全与合规基线

- 上传、查看、下载和后台任务执行都进行服务端授权校验，严禁仅依赖前端隐藏。
- 数据传输使用 TLS，数据库和对象存储启用静态加密；密钥放入部署平台的 Secret Manager。
- 向模型供应商发送前去除不必要的联系方式等个人信息，并选择不用于模型训练/满足保留策略的企业 API 配置。
- 明示保存目的与期限，支持删除单个任务、原文件和整个账户；删除覆盖数据库、对象、缓存和异步任务产物。
- 日志、分析和报错系统默认脱敏；不记录简历全文、邮箱、电话、地址或签名下载 URL。
- 防御越权访问、提示注入、恶意文件、资源耗尽和导出模板注入；富文本统一转义/清洗。
- 上线前根据实际服务地区完成隐私政策、服务条款和供应商数据处理协议评审；JobFit 不提供法律结论。

## 12. 推荐目录结构

先保持单仓库；真正进入实现阶段时再按以下结构渐进创建，而不是一次生成全部空目录：

```text
jobfit/
├── README.md
├── docs/
│   ├── product/                 # MVP 验收标准、用户研究、术语
│   ├── architecture/            # ADR、数据流、威胁模型
│   └── ai/                      # 提示词规范、评测集说明（不放真实个人数据）
├── apps/
│   ├── web/
│   │   ├── src/app/             # Next.js 路由与服务端入口
│   │   ├── src/components/      # 通用 UI 与流程组件
│   │   ├── src/features/        # jobs、documents、facts、matches、resumes
│   │   └── tests/               # Web 集成与端到端测试
│   └── worker/
│       └── src/                 # 文档、AI、校验、导出任务消费者
├── packages/
│   ├── db/                      # Prisma schema、迁移、仓储层
│   ├── domain/                  # 实体、状态机、业务规则与共享 Schema
│   ├── ai/                      # Provider 接口、prompts、结构化输出与 guardrails
│   ├── documents/               # PDF/DOCX/OCR 适配器与规范化
│   ├── ui/                      # 可复用设计系统（需要时再拆分）
│   └── config/                  # TypeScript、lint、test 共享配置
├── fixtures/
│   └── synthetic/               # 完全虚构的测试 JD/简历，不含真实用户数据
```

领域代码优先按业务能力组织，避免出现容纳所有逻辑的 `utils`。外部 OCR、LLM、存储和认证都通过适配器接入，领域层只依赖内部接口与 Schema。

## 13. 分阶段交付建议

1. **原型验证**：用脱敏/合成数据走通页面线框，验证用户是否理解“要求—事实—改写”的引用关系。
2. **可信数据链**：实现认证、JD/简历文本输入、结构化事实确认、数据库权限和状态机；先不追求复杂文件。
3. **AI 闭环**：依次加入 JD 分析、匹配、受约束生成和校验评测；每步均可人工修正。
4. **文件与导出**：接入 PDF/DOCX、OCR、固定模板导出及失败重试。
5. **封闭测试**：使用合成数据自动评测，再邀请少量学生测试可用性、真实性和删除流程。

在开始编码前应补齐：MVP 页面线框、数据保留期限、文件上限、模型供应商评估、事实性评测集，以及每个表格行中验收标准对应的测试方案。

## 14. MVP 成功指标

- 主流程完成率：成功从 JD 输入到 PDF 导出的任务占比；
- 首次可用时间：从创建任务到出现第一版可审阅草稿的中位时长；
- 事实可靠性：自动测试与人工抽检中的无证据主张率必须为 0；
- 可解释性：生成要点事实引用完整率，以及用户能否正确理解引用来源；
- 编辑质量：建议接受/编辑/拒绝比例与编辑距离（不把高接受率单独视为成功）；
- 解析质量：JD/简历抽取后需要用户修正的字段比例，按文件类型区分；
- 隐私可靠性：跨用户访问测试、删除流程测试和敏感日志扫描全部通过。

这些指标用于判断是否值得扩展功能，而不是生成对用户不透明的“综合求职分数”。
